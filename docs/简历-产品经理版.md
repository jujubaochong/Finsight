- **懂技术、能落地**：独立用 FastAPI + React/TypeScript 把产品全栈实现并部署上线；过程中定位并修复了搜索/详情接口超时、服务启动假死等线上级稳定性问题。

## 二、按 PM 能力维度的项目详述

### 1. 产品定位与价值主张
- 一句话价值主张刻意覆盖四要素——**目标用户**（有研究意愿的个人投资者）、**场景**（研究一只股票）、**核心能力**（AI 多维分析）、**用户价值**（替代在 3~4 个 App 间来回查找的碎片化体验）。
- 提炼并排序了 4 个核心痛点：信息碎片化 → 看不懂原始数据 → 信息筛选效率低 → 缺乏分析框架。

### 2. 竞品分析（结论导向，非功能罗列）
- 方法：每款产品实际使用 ≥30 分钟，模拟真实投研场景记录可复现的体验问题。
- 产出竞品能力矩阵（财务数据深度 / AI 分析质量 / UGC / 易用性 / 报告生成 / 主动风险发现 / 价格 / 目标用户）。
- 核心洞察：竞品都扎堆在"面向散户的轻量问答"和"面向机构的专业终端"两端，**中间缺一款给'想深研但够不着机构工具'用户的 AI 分析产品**——这就是 FinSight 的卡位。
- 还做了"如果竞品抄了我们怎么办"的防御推演，沉淀出三条护城河：分析框架×AI、用户数据飞轮、极致聚焦的体验差。

### 3. 用户研究
- 3 个用户画像均落到"典型的一天"的具体生活场景，而非抽象标签：
  - **张弛**（小白研究者）：想研究但被工具劝退 → MVP 主攻人群（量大、最痛）。
  - **赵明远**（小型 FA 分析师）：用散户工具做专业活、负担不起 Wind → V1 扩展（频次最高、商业化潜力最大）。
  - **林薇**（CPA 背景独立研究者）：能力强但工具停留在 Excel+PDF 时代 → V2 覆盖（驱动产品深度）。
- 明确"非目标用户"（短线/打板/纯基金/跟单族），作为后续抵御需求蔓延的判断依据。

### 4. 需求定义与优先级
- 用 **MoSCoW** 排定 Must/Should/Could/Won't，每条都给出理由。
- 主动维护"不做清单"（交易下单、买卖建议、实时行情/K线、社区 UGC、港美股），每条附战略理由——是"刻意聚焦"而非"资源不足"。

### 5. PRD 与产品设计
- 输出 4 大功能模块 PRD：股票搜索与信息聚合、AI 分析引擎、报告生成、自选股异动监控。
- 每个关键设计决策都用 **Q&A + 取舍理由** 写清楚（例：为何搜索直达详情页而非列表页；为何分快速/深度两层分析；异动监控为何只盯基本面变化、不盯涨跌幅）。
- 系统覆盖**边界情况**（无效代码、退市股、接口超时、数据缺失等）与**非功能性需求**（搜索 <500ms、AI 快速分析 <10s、报告 <2min 等目标值）。

### 6. AI 产品策略
- 双层能力设计：快速分析（<10s，详情页内嵌，约 1/5 token 成本）与深度研报（异步任务，7 章结构）对应不同场景与成本。
- 防幻觉三层防线：① 数字强制引用源数据不允许 AI 自行计算 ② 每个数据标注来源可追溯 ③ AI 推断内容与数据事实显式区分。
- 合规设计：只做"客观分析"不做"买卖建议"，风险用温和措辞避免诱发恐慌操作。

### 7. 数据指标体系
- **北极星指标**：周活跃搜索用户数（同时反映"获客"与"首体验价值"），并说明了为何不选"报告生成数"。
- 转化漏斗：访问 → 搜索 → 看详情 → 停留 >30s → 生成报告/加自选 → 次周回访，逐环节设目标转化率与流失排查方向。
- 质量指标：AI 数据准确率 >95%、幻觉率 <5%、报告完成率 >95%；体验 P95 指标；留存（次日/7日/30日）与 NPS。
- 设计 4 组 A/B 实验假设（如"详情页首屏先放风险还是先放亮点对停留时长的影响"）。

### 8. 路线图与风险管理
- 分三阶段：MVP（验证"AI 研报比碎片化问答更有价值"的核心假设）→ V1（行业对标 + 自选监控，从"能用"到"好用"）→ V2（批量赛道扫描 + 多市场，从"工具"到"平台"）。
- 维护风险登记表（数据源停更、AI 质量不达预期、API 涨价、竞品跟进等）并给出应对（备用数据源、规则引擎保底、模型可切换等）。

### 9. 落地交付（PM 的稀缺加分项）
- 独立用 FastAPI + SQLAlchemy（后端）、React + TypeScript + Vite + Tailwind（前端）把产品全栈实现并部署上线。
- 用 AkShare 接入真实 A 股数据，集成 DeepSeek 大模型实现分析与研报生成。
- 亲历并解决线上级稳定性问题：把搜索/详情/刷新的同步阻塞拉取重构为后台异步 + 渐进式加载（消除前端 60s 超时）；定位并修复服务启动时"逐只同步拉财务"导致的启动假死。
- 价值：能与研发用同一套语言对话，PRD 可直接落地，对技术可行性与成本有判断力。

## 四、面试讲解脚本

### 故事 A：用竞品分析找到产品卡位（讲"产品 sense"）
- **背景**：AI 炒股助手已经很多，凭什么再做一个？
- **动作**：我实际把同花顺问财、东财妙想、雪球 AI、Wind 各用了半小时以上，发现它们的共同盲区——都在"给你看数据"，没人"帮你理解数据"，更没人主动发现风险或生成结构化研报。
- **结论**：我把 FinSight 卡在"轻量问答"和"机构终端"之间的空白地带，差异化定在"主动风险发现 + 一键研报"，并预演了竞品跟进时的三条护城河。

### 故事 B：用优先级和"不做清单"控制范围（讲"取舍力"）
- **背景**：一个人做 0→1，最大风险是范围失控。
- **动作**：用 MoSCoW 把需求切成四档，并显式维护"不做清单"（交易、荐股、K线、社区、港美股），每条都写明战略理由。
- **结论**：MVP 范围压到单人可交付，且后续遇到"能不能加 K 线"这类需求时，能用"非目标用户"原则快速判断不做。

### 故事 C：把"启动假死"定位成产品+技术问题（讲"落地力"）
- **S**：后端启动时好时坏，有时秒起、有时卡住像死循环。
- **T**：找出为什么是"间歇性"的并彻底修复。
- **A**：对比日志和数据库状态，定位到启动钩子里同步执行行业基准计算——它会按行业遍历全部股票、对缺数据者逐只发起带重试的网络请求；当数据库已有行业分类时退化成数千次同步调用。修复：给数据获取加只读开关、把重活移到后台任务、让服务先就绪。
- **R**：启动从数分钟阻塞降到秒级，并补了回归测试。这个故事能体现我"既懂产品体验、也能下沉到技术根因"。
